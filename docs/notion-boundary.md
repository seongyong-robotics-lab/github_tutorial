# Notion ↔ GitHub 경계 규칙

> Stage 0에서 직접 채웁니다. 이걸 안 정하고 시작하면 반드시 양쪽이 어긋납니다.

## 3줄 규칙

```
1. "왜 만드는가" (요구사항, 설계, 결정 근거)  →  Notion
2. "무엇을 하는가" (작업, 버그, 코드)          →  GitHub
3. 둘은 ID로 연결한다. Notion REQ-012 ↔ GitHub 이슈 제목 [REQ-012]
```

## 항목별 원본(source of truth)

| 정보 | 원본 | 반대쪽은 |
|---|---|---|
| 요구사항 내용 | Notion | 참조 링크만 |
| 요구사항 승인 여부 | Notion | — |
| 설계 문서 / ADR | Notion | 링크 |
| 작업 진행 상태 | GitHub | 자동 동기화된 미러 |
| 코드 변경 이력 | GitHub | — |
| 스프린트 계획 | GitHub Project | — |
| 회의록 | Notion | — |

## 직접 채우기

내 프로젝트(임베디드 통신 스택)에서 애매한 것 3개와 그 판단:

- **테스트 케이스** → **양쪽으로 쪼갠다.**
  "무엇을 검증해야 하는가"(검증 항목, 커버리지 목표, 합격 기준)는 **Notion** — 요구사항에서 파생되고 시스템 엔지니어가 고친다.
  "어떻게 검증하는가"(테스트 스위트 코드)는 **GitHub** — 코드와 같은 커밋에서 함께 바뀌어야 하므로.
  → 판단 근거: 테스트가 틀렸을 때 *기준*이 틀렸으면 SE가, *구현*이 틀렸으면 개발자가 고치러 간다.

- **인터페이스 정의(ICD) / 메시지 카탈로그** → **GitHub이 원본.**
  코드 생성을 구동하는 정의 파일이 repo에 있으므로, Notion ICD 문서가 이것과 다르면 **틀린 쪽은 항상 Notion**이다.
  Notion에는 "왜 이 ID 체계인가 / 계층 간 라우팅 규칙"만 두고, 표 자체는 링크 또는 생성된 미러로.
  → 판단 근거: 값이 틀리면 개발자가 정의 파일을 고치고 재생성한다.

- **HIL / 실기 테스트 결과** → **결과는 GitHub, 판정은 Notion.**
  실행 로그·수치·아티팩트는 GitHub(Actions 아티팩트 / Release 첨부)에 남기고,
  "이 결과로 릴리스를 승인한다"는 **결정**은 Notion에 남긴다.
  → 판단 근거: 숫자가 틀렸으면 다시 돌리는 건 개발자, 승인 판단이 틀렸으면 고치는 건 PM/SE.

## 판단 기준

애매하면 이렇게 물어보세요.

> **"이 정보가 틀렸을 때, 누가 고치러 가는가?"**

개발자가 고치러 간다면 GitHub, PM/시스템 엔지니어가 고치러 간다면 Notion입니다.

## 자동화를 붙이고 나서 다시 다듬은 것 (Stage 6)

### 1. 경계는 문서가 아니라 **스키마**에 있어야 한다

처음 SYS-REQ DB 를 만들 때 `상태` 속성 하나에 이렇게 담았다.

```
초안 / 승인            ← 요구사항 승인 여부.  Notion 이 원본
구현 중 / 완료 / 보류   ← 작업 진행 상태.      GitHub 이 원본
```

**한 칸에 원본이 다른 두 정보가 섞여 있었다.** 자동화를 붙이자 곧바로 드러났다 —
`초안` 인 요구사항의 이슈가 닫히면 Notion 이 `완료` 로 덮어쓴다. 승인도 안 된 요구사항이
완료가 되는 것이고, 이 문서 위쪽 표를 자동화가 어기는 셈이다.

속성을 쪼갰다.

| 속성 | 원본 | 누가 쓰는가 |
|---|---|---|
| `승인 상태` (초안/검토 중/승인/폐기) | **Notion** | 사람만 |
| `구현 상태` (미착수/구현 중/완료/보류) | **GitHub** | `sync-notion` 워크플로만 |

> 경계 규칙을 문서에만 적어두면 지켜지지 않는다. **필드를 나누면 어길 방법이 없어진다.**
> 라벨 대신 Project 필드를 쓴 이유와 같은 구조다.

### 2. 미러 쪽을 사람이 고치면 **경고 없이 사라진다**

💥 실험: Notion 에서 `구현 상태` 를 `보류` 로 바꾼 뒤, GitHub 에서 이슈를 reopen 했다.

```
Notion 에서 사람이 '보류' 로 변경
   ↓
GitHub 이슈 reopen
   ↓
[ok] REQ-003 -> 구현 중 (남은 열린 이슈 1건)
   ↓
Notion = 구현 중        ← '보류' 가 흔적 없이 사라짐
```

**"어느 쪽이 이기는가"는 잘못된 질문이었다.** 경쟁이 아니다.
Notion 의 편집은 아무 데도 전파되지 않았고, GitHub 은 그런 변경이 있었는지도 모른다.
다음 이벤트가 그냥 덮어썼을 뿐이다. **그리고 편집한 사람은 아무 알림도 받지 못한다.**

어긋나는 것보다 나쁘다. 어긋나면 눈에 띄기라도 한다.

→ 그래서 `구현 상태` 속성 설명에 *"사람이 직접 고치지 말 것"* 을 적고,
각 REQ 페이지 본문에도 경계 표를 넣었다. **규칙은 사람이 실수하는 바로 그 자리에 있어야 한다.**

### 3. 동기화는 **한 방향만**

Notion → GitHub 방향은 만들지 않았다. 기능 누락이 아니라 결정이다.

- 양방향이면 어느 쪽이 원본인지 알 수 없어진다
- 두 자동화가 서로를 트리거해 루프가 된다

요구사항 *내용* 을 바꾸고 싶으면 Notion 에서 고치고, 이슈는 사람이 다시 읽는다.
**"자동으로 반영"의 반대는 "수동"이 아니라 "사람이 판단한다" 이다.**

### 4. 조용한 실패가 최악이다

존재하지 않는 `REQ-999` 로 실험했을 때 워크플로는 **실패해야 한다.**

```
##[error]Notion 에 REQ-999 페이지가 없습니다.
##[error]Process completed with exit code 1.
```

동기화가 없으면 사람이 확인한다. **있다고 믿으면 아무도 안 본다.**
그래서 REQ ID 오타는 조용히 넘기지 않고 빨간 X 를 띄운다.
반대로 REQ ID 가 아예 없는 이슈(잡무, 아이디어)는 정상 종료한다 —
모든 이슈가 요구사항에서 나오지는 않는다.

### 5. 판단 단위는 이슈가 아니라 **REQ 전체**

하나의 REQ 에 이슈가 여러 개 걸린다. 이슈 하나가 닫혔다고 REQ 가 끝난 게 아니다.

```
#5 닫힘   → 남은 열린 이슈 2건 → 구현 중
#40 닫힘  → 남은 열린 이슈 1건 → 구현 중
#41 닫힘  → 남은 열린 이슈 0건 → 완료      ← 여기서 넘어간다
```

같은 이유로 **여는 쪽도 봐야 한다.** 처음에는 `closed`/`reopened` 만 트리거로 잡았는데,
완료된 REQ 에 새 이슈가 열려도 Notion 이 `완료` 로 남는 구멍이 있었다.
자동화는 상태 전이를 **양쪽 다** 덮어야 하는데, 만들 때는 눈앞의 시나리오(닫기)만 보게 된다.
